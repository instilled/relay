# Flows: recurring work, with your review, in one place

Status: design, for review · 2026-10-07

## Why

Relay's worth is recurring work that goes on without you, with the actions that matter left to
your yes. Today one such job is spread across a `schedules.yaml` entry, a probe that `rl emit`s,
a rule in `reactions.yaml`, and an agent prompt that must remember to `rl ask` with the right
options. The chain exists only once it has run — the graph and the events view guess it back —
and review is the agent's to forget.

A **flow** is that job as one thing: a trigger, steps, and the review as a step Relay itself
raises. Flows replace schedules and reactions outright. There is no release yet, so nothing is
kept for them: no alias, no migration of rules, no legacy files.

Two flows are the measure of this design:

- **prod-logs** — every 30 minutes, a probe finds new errors and warnings in flint-platform's
  logs; when there are any, an agent analyses them and proposes one action; you approve it, and
  an agent does it, or you ignore it.
- **morning-brief** — weekday mornings, three sources (gchat, notion, github) say what the team
  worked on yesterday, and an agent writes a super high-level brief per teammate, waiting for you
  at the top of the catch-up.

## A flow is a folder

Flows live in the Relay home only — `~/.relay/flows/<name>/`, the folder's name the flow's.
A checkout's `.relay/` never holds one, so cloning a repo can never make Relay run anything.

```
~/.relay/flows/
  .gitignore             written by rld: runs/
  prod-logs/
    flow.md              the definition: YAML frontmatter, prompts as `## <step>` sections
    new-log-errors.sh    the flow's own scripts — first on its steps' PATH
    runs/<firing>/       one firing's state ($RELAY_WORK)
  morning-brief/
    flow.md
    runs/…
```

`~/.relay/flows/` may be a git repository — history with `git log`, sharing with a push — and
Relay neither needs nor assumes it.

```markdown
---
in: ~/Projects/flint-platform
when: every 30m
steps:
  probe:
    run: new-log-errors.sh
  triage:
    after: probe
    if: probe.out
    run: { agent: claude }
  review:
    after: triage
    ask: "{triage.out}"
    group: "{probe.signature}"
    options:
      apply:  { run: { agent: claude } }
      ignore: {}
    default: ignore
    expires: 4h
---

## triage
Analyse the new errors and warnings below. Propose exactly one action, in two lines at most.

{probe.out}

## review.apply
Do this, in this repository: {triage.out}

What was said with the yes: {review.note}
```

```markdown
---
when: "30 7 * * 1-5"
catch_up: top
steps:
  gchat:  { run: { agent: claude, args: [--allowedTools, "mcp__gchat__*,Bash(rl flow state:*)"] } }
  notion: { run: { agent: claude, args: [--allowedTools, "mcp__notion__*,Bash(rl flow state:*)"] } }
  github: { run: "gh search prs --involves=@me --updated=>$(date -v-1d +%F) --json title,author,url" }
  brief:
    after: [gchat, notion, github]
    run: { agent: claude }
---

## gchat
What did each of my teammates talk about in gchat yesterday? One line each.

## notion
…

## brief
Super high-level, one or two lines per teammate, what they worked on yesterday:

{gchat.out}
{notion.out}
{github.out}
```

### The frontmatter

| key | what |
|---|---|
| `in` | the workspace the steps run in — a path (`~` allowed), never a name, so a rename (`^r`) cannot break it. It must be a project Relay knows, or the flow does not load. A step's own `in` overrides it. |
| `when` | a cadence: `every 30m`, or a five-field cron line in quotes, local time |
| `on` | event kinds (`run.failed`, `logs.*`, `*`), with `where` to narrow (`tag`, `cause`, `cli`, `group`, `data`) — today's reaction matching, unchanged |
| neither | the flow runs only when asked (`rl flow run`, `/flow run`) |
| `missed` | `catch-up-once` (default) or `skip` — a `when` firing slept through; a yes or an edit plans an `every` from now, so it neither fires nor is missed at once |
| `overlap` | `skip` (default), `queue` or `kill` — a trigger while the last firing still runs; a queued `when` firing waits however long, and is late only from when the last one ended |
| `throttle` | for `on`: a burst within it is one firing (default 10s) |
| `catch_up` | `top`: its latest firing since you left heads the catch-up (below) |
| `steps` | the steps, by name |

`when` and `on` may both be given; either fires it.

### Steps

A step is one of two things, plus when it runs:

- **`run:`** — the action form Relay already has, unchanged: a string through `sh -c`, a list as
  argv, a map as an agent run headless (`agent`, `prompt` / `prompt_file`, `args`, `model`), with
  `cwd`, `env`, `tags`, `title` around it. An agent step with no prompt takes its `## <step>`
  section. Steps run without a tty.
- **`ask:`** — a question Relay raises, the text built from what came before, with `options`
  (each an action, `{}` doing nothing), `default`, `expires`, `group` (an open question with the
  same group is restated, not asked again — so one error does not ask every 30 minutes; a plain
  `rl ask` in that group asks its own, and is never restated by a step, nor restates one) and
  `multi`. An option's agent with no prompt takes the `## <step>.<option>` section.
- **`after:`** — a step name or a list. None: the step starts when the firing does. Steps ready
  together start together.
- **`if:`** — `probe.out`, `probe.severity`, `!probe.out`, `review.choice == apply`,
  `probe.severity != low`. A bare name is true when it is set and not empty. Nothing more: no
  `&&`, no arithmetic — a step that needs more computes it and sets a value.
- **`in:`** — overrides the flow's.

Where a step runs: its `in`, else the flow's; with neither, a step of an `on` flow runs where the
event happened (the folder of the event's run while it is there, else the event's workspace),
and anything else in the Relay home.

What is wrong is said at load, with the file and line: an unknown `after`, a cycle, an agent step
with neither a prompt nor a section, a `prompt_file` that is not in the flow's folder (absolute,
out through `..`, or under `runs/`, which no hash covers), a `multi` ask with more than one option that runs something (until every
chosen option runs, only one may), a link to a folder inside the flow's folder (what is under it
would run without being hashed), an `if:` naming a step it does not come after, an `in` Relay
does not know (`prod-logs · flow.md:3 · in: ~/x is not a project Relay knows · rl add ~/x`; `rl add` is `rl up` by another name).

## State between steps

Three layers, each opt-in:

| | a step does | later steps get |
|---|---|---|
| **out** | nothing | `{probe.out}`, `rl flow state read probe.out`, `$RELAY_IN/probe.out` — a command's output, an agent's final message, ANSI stripped |
| **values** | `rl flow state set signature=abc found=3`, or `k=v` lines appended to `$RELAY_OUT` | `{probe.signature}`, in `if:` and `group:`, `rl flow state get probe.signature` |
| **files** | `rl flow state write report.md < x`, or a file in `$RELAY_WORK` | the same folder, `rl flow state read report.md` |

An `ask` step's values are `choice` and `note`: `{review.choice}`, `{review.note}`. An event's
are `{event.summary}`, `{event.run}`, `{event.data.x}`, and `$RELAY_EVENT` holds it whole.

**`rl flow state set|get|write|read`** is what a step uses. Every step starts with `RELAY_RUN`,
`RELAY_FLOW`, `RELAY_FIRING`, `RELAY_STEP`, `RELAY_WORK`, `RELAY_FLOW_DIR`, `RELAY_IN` and
`RELAY_OUT` set, so it needs no arguments to land in the right firing; outside a step it refuses
(`not in a flow step`). It goes through `rld`, not to disk, because an agent's permissions may not
reach `~/.relay` while `Bash(rl flow state:*)` is one allow rule — and that rule gives an agent
its firing's state and nothing else: it cannot approve, run or edit a flow. `rld` checks the
name (no `/`, no `..`), caps a value at 4 KB and a file at 10 MB, and writes atomically. A plain
script may write `$RELAY_WORK` and `$RELAY_OUT` itself. The `rl` a step finds is the one beside
the `rld` running it, next on its `PATH` after the flow's folder.

**Placeholders are spliced only into prompts and `ask:` text.** A `run:` string or argv never
gets them — a command reads `$RELAY_IN/<step>.out`, or `$RELAY_V_<step>_<key>` from its
environment — so an error line in production logs can never become shell. A `run:` that names a
placeholder (`{probe.out}`) is refused at load, saying which variable to read instead; other
braces (`awk '{print $1}'`) are the shell's.

Across firings there is no state in this design: `RELAY_LAST_FIRING` (when the last firing
started) lets a probe ask for only what is new, and `group:` restates an open question. A
`rl flow state` that outlives a firing comes if a flow needs it.

## The engine

A firing is a small state machine in `rld`, decided by pure code (`rl-flow/advance.rs`) and
carried out by the daemon:

- **States.** A firing is `running`, `waiting` (on a question, or a lost step), `done`, `failed`
  or `stopped`. A step is `pending`, `running`, `waiting`, `done`, `skipped` or `failed`.
- **Advancing.** On a step's run ending, on an answer, on an expiry and when `rld` starts, the
  engine takes each pending step whose `after` are all `done`: its `if:` false, it is `skipped`
  and so is everything after it; true, it starts. A step whose run ends in failure is `failed`,
  and what comes after it is `skipped`. With nothing pending or running, the firing ends —
  `failed` if any step failed, else `done`.
- **Fan-in.** A join runs only when everything it waits on is `done`. A failed source means no
  brief that morning, and the catch-up says why. Partial joins are not in this.
- **Questions.** An `ask` step raises an ordinary question — on top of the list and the catch-up,
  answerable by number with a note, expiring to its `default`. The firing is `waiting` and
  nothing blocks. The option chosen runs as the step's own continuation; its out is the step's.
- **Restarts.** When `rld` starts it reconciles: a step whose run ended while it was down
  advances; one whose run was lost leaves its firing `waiting · lost`, and `/resume` (or `rl
  resume`) picks the step up in the same firing, with the same state.
- **Causes.** A step's run is `cause: flow:<flow>/<step>` (the `workflow:` reserved so far
  becomes `flow:`, one word everywhere) and its `Run.flow` is the firing's
  id, so the events view, `/summary` and the chain already know what it is.
- **Events.** `flow.fired` (the trigger, and the event that fired it) and `flow.ended` (how);
  the steps' runs raise `run.*` as any run does. `schedule.fired` goes.

**Between flows there are only events.** A flow never starts another: one flow's runs raise
events — Relay's own or `rl emit`'s — and another's `on:` hears them. A step that truly needs
another flow runs `rl flow run <name>`, and the chain says so. A run a flow started never fires
that same flow, and the reactor's cursor and five-minute horizon stay, so a daemon that was down
does not fire a day of history.

## Loading and approval

`rld` loads every `~/.relay/flows/*/flow.md` at start, on `rl flow reload` and the panel's
`/reload`, and after `rl flow new` and `rl flow edit`. A flow that does not load is left out,
said with file and line — `rl flow list`, a red `! flows` on everywhere's header, its pane — and
the rest load; a folder that cannot be read leaves that flow as it last loaded.

A flow runs only once approved, by the hash of its folder less `runs/`, so changing a script asks
again, as the frontmatter does. The folder is hashed again before a firing starts and before
each step does: one changed since its yes is not fired, and a step on it does not start
(`flow.skipped`, "the flow changed since its yes"), reload or no reload; and a step starts only
while the yes is still to the version its firing began on ("the flow changed since this firing
began" otherwise). A yes is to the version
shown: `flow.approve` carries its hash and is refused once the folder as loaded is another.
Writing it through `rl` is the yes: `rl flow new`, `/flow new`'s enter, and an `rl flow edit` /
`/flow edit` that saves a changed `flow.md` that loads — when the folder had its yes before the
editor opened and nothing else in it changed meanwhile; else it is left needing one, and says
why. A new flow left as the template is not kept, however the editor ends — its `flow.md` goes,
its folder only if nothing else is in it. Anything else — a hand edit outside `rl`, a
flow an agent wrote — shows `! needs a yes` until `/flow approve`.

## Where you see it

- **The list.** A flow is one row in its `in` project (everywhere without one), its steps' runs
  folded into it as a schedule's are today: `↻ prod-logs  ··✓×✓  waiting at review · page on-call?
  2h`. Expanded, the latest firing's steps: `probe ✓ · triage ✓ · review ?`. Its question is a
  needs-you row on top, as any question is. The pane: the trigger, the steps, the last firings,
  approval, the latest firing's state files; `enter` on a step joins its run.
- **The catch-up.** A flow is a line under its project: its firings as marks, then the outcome —
  the first line of the last step's out. A `catch_up: top` flow's latest firing since you left
  heads the catch-up, above Relay's own bullets, under its name, the whole of it in the pane.
  `/summary [deep]` works on a flow and on one firing.
- **The graph.** Steps are nodes, grouped under their flow, the trigger on the left (`◷ every
  30m`, `◆ run.failed`). Within a flow the edges are declared; between flows they are the events
  that went across, labelled and counted, and an `on:` nothing raised yet is a dangling `◆` way
  in. `emits:` goes.
- **The events view.** What a flow set off is read from the cause, so it is exact; the guessing
  for runs and questions from before reactions kept their event goes.
- **Commands.** The panel and `rl` say the same words:

  ```
  rl flow list                       /flow …        every flow, its hash, how it stands, what did not load
  rl flow new <name> [words…]        /flow new      words: drafted by assistants.interpret;
                                                    none: a template in $EDITOR
  rl flow edit <name>                /flow edit     flow.md in $EDITOR
  rl flow run <name> [--step s --firing id]         now; one step again against a past firing
  rl flow pause|resume <name>
  rl flow approve <name> [<hash>]    /flow approve  read again; a yes only to the version the hash
                                                    (or 6+ of it) names; none: the one read, printed
  rl flow test <name> [--event id]   /flow test     what would fire, which steps would run; starts nothing
  rl flow reload
  rl flow state set|get|write|read                  inside a step
  ```

  On a flow row, or a step in the graph, `/flow …` acts on that flow; elsewhere it completes the
  name. `/new` starts a run and nothing else; `/approve`, `/pause` and `/edit` go with the rules
  they acted on.
- **Drafting.** The interpreter answers `kind: run` or a whole `flow.md`; the panel shows the
  draft, and enter writes the folder and approves it. A draft is `flow.md` alone — a script it
  needs is yours, or an agent's, to add. The context pack teaches flows, steps, `if:`, the
  placeholders and `rl flow state`, built from the code as today so it cannot drift.

## What goes, and what stays

Goes: `schedules.yaml` and `reactions.yaml`, home and folder alike; `rl-core`'s `rules_dir`; the
`schedules`, `reactions` and rule tables (one migration drops them; nothing is carried over);
`rl schedule`, `rl react`, `rl every`, `rl on`, `rl rules`, and `rl up`'s loading of rules; the
`Rule` enum, `rulefile.rs`, `rulestore.rs`, `tui/rules.rs`; `emits:`; `schedule.fired`; the
events view's inference; schedules and reactions in the context pack.

Stays, moved where it belongs: the cron parser and the scheduler loop (as `when`), the reactor
loop with its matching, throttle, cursor and no self-feeding (as `on`), the question engine,
the action parser, the graph's layout, not-loaded reporting.

`PROTOCOL_VERSION` is 4. On the one install there is a commented-out schedule and an empty
`reactions.yaml`; both are removed by hand when this merges.

## Modules

All the deciding is pure and lives in a new crate; the daemon carries its answers out.

```
rl-flow (new — no I/O, no tokio; on rl-proto, rl-core)
  doc.rs        flow.md → FlowDef: the frontmatter and `## step` sections, errors at line:col
  def.rs        FlowDef, Trigger (When | On), Step (Run | Ask), validation
  plan.rs       the step DAG: order, what each step waits on, cycles
  advance.rs    (firing, what happened) → what to do: start, skip, ask, end
  cond.rs       `if:`
  template.rs   placeholders: into prompts and `ask:`; env and files for commands
  cron.rs       moved from rl-daemon/src/schedule/cron.rs
  hash.rs       a folder's approval hash, from (path, bytes) pairs handed in

rl-proto        flow.rs (Flow, Firing, StepState, NotLoaded); flow.* in methods.rs;
                schedule.rs, reaction.rs, rule.rs gone
rl-ledger       flows.rs (approvals, paused); firings.rs (firings, steps, values);
                schedules.rs, reactions.rs gone; graph.rs reads firings
rl-core         Home: flows(), flow_dir(name), firing_dir(name, id); rules_dir.rs gone
rl-daemon       flows/{mod.rs the service · store.rs load, not-loaded, approval ·
                engine.rs carries out advance · triggers.rs when and on · state.rs
                `rl flow state` and runs/ · rpc.rs the flow.* handlers};
                schedule/, reactions.rs, rulestore.rs gone
rl-cli          flow.rs (`rl flow`); tui/flows.rs (the row, its steps, the pane);
                tui/graph.rs fed flows and steps; rulefile.rs, tui/rules.rs gone
```

- One set of words everywhere: flow, firing, step, trigger. No `rule`, `schedule` or `reaction`
  is left in a name, type, method, event, table or the context pack; the last PR greps for it.
- No module past about 800 lines; `handlers.rs` hands its rule handlers to `flows/rpc.rs`.
- What a PR replaces it deletes — no shims, nothing dead.
- `ARCHITECTURE.md` §6 becomes "Flows" and the crate diagram gains `rl-flow`, in the PR that
  makes them so.

## The PRs

Each one green and usable on its own:

1. **Flows replace rules.** The folder, `flow.md`, loading and approval; the engine (steps,
   `after`, `if`, fan-in, overlap, restart, resume); `when` and `on`; `ask` steps; out (`{x.out}`
   in prompts and `ask:`); `rl flow` but `new` and `state`; the flow row on the list; the
   events; every schedule and reaction surface removed. The big one — keeping both alive across
   two PRs would cost more than it saves.
2. **State.** `rl flow state`, values, `$RELAY_WORK` and `runs/<firing>/`, the env, the caps,
   retention of `runs/` with its firing's runs.
3. **Seeing it.** The graph and the catch-up for flows, `catch_up: top`, `/summary` on a flow and a
   firing, the pane.
4. **Writing it.** `rl flow new` and `/flow new` with words, the context pack, `rl flow test`, and
   prod-logs and morning-brief as templates (`rl flow new prod-logs --from prod-logs`).

## Not in this

- A worktree per agent step — `apply` works in the checkout, with your yes each time. Next.
- Partial fan-in, state across firings, `&&` in `if:`.
- Telling you elsewhere (Slack, mail, phone): a flow can, with a step; a built-in `notify:` later.
- Sharing (`rl flow add <repo>/flows/x`), a watcher on `~/.relay/flows/`.

## Testing

- **Pure** (`rl-flow`): `flow.md` parsed, sections found, each load error at its line; the
  plan's order and cycles; `advance` over ready, skipped, failed, fan-in, an answer, an expiry,
  lost; `if:`; placeholders into prompts and never into a command; the hash moving when a
  script does.
- **Daemon**, with the fake agent, never a real one: a three-step firing end to end; `if:`
  skipping; an `ask` answered (choice and note reaching the option's run) and expiring to its
  default; `group` restating; overlap; `on` with `where`, and a flow not firing itself; a restart
  mid-firing, then resume; approval by hash and a changed script asking again; an unknown `in`
  not loading; `rl flow state` refused outside a step, its caps and names.
- **Panel**: the flow row folding and expanding; `/flow …`; a review answered from the list and
  from the catch-up; `catch_up: top` heading it.
- **Live**, in an isolated `RELAY_HOME`, both flows with stub probes and the fake agent.
